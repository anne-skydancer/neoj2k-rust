# Continuing zero-dependency tuning checkpoint

These are intermediate experiments, not final acceptance evidence. The initial audit report remains frozen. Production Windows source currently uses the dense low/high-band DWT with unchanged eight-row scratch size, the colder quantizer fallback, the two-channel long-row packing hybrid, and the safe f64 general finish. The validated flattened DWT lifting body is now ported to Windows too. High-precision MCT tuning continues, with no accepted production alternative to the f64 finish yet.

The dense horizontal row kernel closed most of the original small-image wavelet gap. Its two independent reference tests cover odd widths, both parities, padded/offset rows, poisoned scratch and nonfinite finishing. Current Linux full release native/C++ unit suite passes 106 tests (seven ignored). Actual nightly-2026-11-03 Miri has now passed four focused tests on the live Windows snapshot: dense finite/parity/padding DWT, nonfinite DWT finishing, all-precision wide finishing, and packing boundary/padding. Each ran under an independent 180-second timeout; total measured host wall time was about 21 seconds. Raw logs and miri-dense-wide-packing-summary.json are saved. This focused interpreter validation does not replace the full native suites.

A single full default-feature v3 process with the flattened lifting body produced exact outputs on all 32 rows. Examples: 64 whole +1.50% (unchanged control -0.57%); 128 whole +1.54% (+0.42%); packed RGBA full -1.44% (+1.83%); large RGB -1.75% (+0.46%). Gray controls moved 9–14%, preventing strict acceptance there. A first reduced packed three-channel row showed +6.71% (+2.15%), but three subsequent pinned processes gave +1.11/+2.72/+2.96% with unchanged controls +3.39/+6.72/+4.93%. Reduced four-channel v3 rows gave +7.36/+8.08/+5.44% with controls +5.38/+4.43/+8.86%. Controls remain too mobile for strict acceptance. This is not a no-regression conclusion.

Additional precision-24/31 SIZ variants preserve the coefficient payload but raise component precision. All three Rust variants and the matched AVX2 C++ oracle produce identical samples and successful status. They expose real general-finish slowdowns: initial best-f64 public measurements include 128 precision31 +7.42% (control -0.62%), large RGB precision31 +5.29% (-0.46%). Stage profiling identifies colour finishing: large precision31 455 versus 255 microseconds, and 128 colour 6.66 versus 3.86, plus component finish 1.55 versus 0.83. These rows remain explicit acceptance work.

The high/low f32 mantissa-bias prototype matched roughly two million float patterns and tie neighbors against original intrinsic conversion for all precisions and signed/unsigned finishes. A fused microbenchmark improved versus an older f64 array prototype, but its public results did not improve consistently, so it was not ported. Those older prototype timings do not describe the current production f64 kernel: a later parent-led microbenchmark with runtime-blackboxed finish parameters found the current production implementation substantially faster than that prototype. Sequential channel computation, two-pass finishing and an explicit mutable-reference alias helper also failed to close the gap. Scalar saturating float conversion, scalar exponent extraction, and per-block range guards were inferior.

The proposed encoder whole-block maximum scan was rejected without a production change. The existing four-sample gather was already much faster than the scalar intrinsic reference in the baseline microbenchmark (32 squared: 186 versus 515 ns); the scan increased this to 554 ns. It does not justify blaming a whole-encoder residual on quantization arithmetic alone.

Reference-only unsafe intrinsics appear in standalone ignored experiment sources; none were introduced into the production crate or its dependency closure. Raw timings describe their named snapshots and must not be combined into an invented final result.


The refreshed baseline full32 process also produced exact outputs throughout. Large RGB one worker improved21.37% (control+0.67%), 128 whole improved16.44% (+1.86%). The earlier lossy-encoder concern was absent in this process:32/64/128 changes -1.57/-0.91/-1.46%, controls+1.98/-1.20/+0.44%. One baseline reduced packed-four row initially showed+4.29%, but three pinned repeats gave -2.75/-2.13/+0.84%, controls+7.33/+2.56/+3.25%; it is not a stable measured loss. These are checkpoint observations, not final platform-wide acceptance.

The corrected encoder micro blackboxes the runtime parameter record and confirms the rejected scan:32 squared current187ns versus original/control514/517ns and scanned556ns. The candidate retains the existing per-four guard.


## Later continuing experiments (supersedes the opening MCT state)

The accepted-for-testing AVX2 uniform high-precision colour implementation now uses a flat per-pixel loop with three separate mutable row arguments and exact high/low f32 bias rounding. Mixed finishes and baseline general finishing retain f64. Explicit eight-element bit-cast constructors prevent out-of-line array mapping calls; identical source clone controls and preserved assembly establish that compiler effect. Independent integrated colour tests cover all31 precisions, signed/unsigned/mixed, exceptional floats and untouched tails. Windows normal native and actual Miri tests pass.

A mathematically equivalent three-operation low-bias expression removes one FP operation. Roughly2.085million independent pattern/tie checks pass; Windows direct paired public precision rows improve large p24/p31 around0.6–1% versus four-operation safe finishing. This is not yet original-performance acceptance. The current Windows worktree is assessing a further signed/unsigned cap specialization and shared unary converter. The combined Linux candidate passes108 native/C++ tests and Clippy; paired public results are mixed, with small64 residuals and no repeatable large-image gain in the combined build. Source and raw evidence are preserved in typed-wide-finishing/.

A separate Linux-only DWT experiment outlines only dense gather and scatter helpers, reducing the row-kernel frame632B to120B. Realistic-stride micro improves9–11%, matching/beating original at widths64/128; full108 native/C++ tests pass. Whole-codec paired timing is prepared and pending the Windows timing window. It is not ported or accepted. The original whole-kernel outlining and fused recurrence variants were rejected; neither changes the Windows best dense implementation.

T1 flat row-store experiments were reverted after real stride and direct paired codec checks showed no reliable overall benefit. Production retains the prior safe store; expanded boundary tests remain. No dependency or unsafe exemption has been added. Performance preservation is still an open requirement.
