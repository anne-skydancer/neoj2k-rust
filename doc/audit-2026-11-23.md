# Specialist audit: Miri, C++ parity and Rust implementation

Audited 2026-11-23 at Rust `f2f52975ece004e1275a3bce6157e5f2f12b61e9`, with the adjacent `neo-j2k` C++ checkout for source comparison. This is an investigation, not an implementation patch. No production code was changed. No new sample-corruption or undefined-behaviour defect was established by this targeted review.

## Findings in priority order

| ID | Priority | Finding | Evidence status |
|---|---|---|---|
| M1 | P1 | Miri's exhaustive arithmetic test consumed the shared job budget, preventing later safety checks | CI confirmed on the previous revision; HEAD mitigation not yet verified under Miri |
| P1 | P1 | Whole-codec speed parity is still unmet, especially small decodes and Linux encodes | Three-repetition CI measurements; production code identical to HEAD |
| M2 | P2 | Successful MQ decisions eagerly allocate and format diagnostics under Miri | Source verified; runtime contribution not separately measured |
| P2 | P2 | Warm parallel decode still allocates and builds serial slice tables | Local allocation reproduction and source verified; speed contribution requires profiling |
| P3 | P2 | Small decode benchmark includes a Rust output copy avoided by its typed API | Source verified; API cost, not a correctness defect |
| P4 | P2 | Encoder comparison covers construction on every request, not reusable encoder throughput | Measurement coverage gap |
| D1 | P3 | Owned reconstruction clears the coefficient plane before a block walk that writes every sample | Source verified redundancy candidate; remove only with coverage proof |

P1 means a stated objective is currently unmet or a CI safety check is unavailable. P2 means an actionable inefficiency or important measurement gap. Priorities do not imply a security vulnerability.

## M1: the 45-minute Miri timeout is test workload

Locations: `.github/workflows/ci.yml:49`, `:70`, `:72`, `:77`; `neo-j2k/src/t1/mq/tests.rs:109` and `:148`.

[Rust CI run 45259752065](https://github.com/anne-skydancer/neoj2k-rust/actions/runs/45259752065), Miri job `137991201834`, started at 20:28:57 UTC and ended at 21:14:13 UTC. Its check annotation explicitly says **“The job has exceeded the maximum execution time of 45m0s”**. The Unit tests step ran 20:29:41–21:14:09 and was cancelled. Decoder requests and AVX2 kernels were skipped. This is an actual timeout, not merely a later push cancelling the concurrency group.

The log completes `a_run_of_aggregate_columns_equals_the_decisions_one_at_a_time` at 20:36:27, then `no_run_when_the_mps_is_one_or_the_room_is_short` at 20:36:28. The remaining select-decision test has no completion before cancellation approximately 37 minutes later. The large Cartesian product explains the apparent hang; there is no evidence here of a codec deadlock.

Before HEAD, the Miri select test checked exactly `94 * (11 + 8) * 7 * 9 * 2 = 225,036` decisions. HEAD reduces this to `94 * (11 + 4) * 7 * 3 * 2 = 59,220`, retaining deliberate interval boundaries. The aggregate test still checks `94 * (8 + 3) * 10 * 6 = 62,040` cases. It also allocates a flag vector inside its innermost loop and copies a decoder containing 32 contexts when comparing sequential decisions.

Commit `42d304b` already fixes an earlier **test-only overflow panic**, replacing subtraction with `wrapping_sub`; HEAD `f2f5297` already reduces select-test sampling. These are existing fixes, not new audit findings. [HEAD CI run 45270209354](https://github.com/anne-skydancer/neoj2k-rust/actions/runs/45270209354) was still running during evidence collection; this report does not claim the timeout is resolved.

Recommended remedy: first remove M2's needless formatting, then time the reduced test under the pinned Miri. Keep broad MQ semantics sweeps in native/oracle tests and a compact representative case matrix in Miri. Put unit tests, decoder requests and AVX2 checks in independent jobs or shards so one arithmetic sweep cannot suppress the other safety checks. Record per-test durations before choosing budgets. Raising the shared timeout alone leaves the coverage coupling intact.

## M2: successful test cases format a message they never use

Location: `neo-j2k/src/t1/mq/tests.rs:103`.

`check_decision` executes `format!("state {index}, from {start:?}, bytes {tail:02x?}")` before its assertions. Every successful case allocates a string, formats all fields of `Model`, and formats four bytes as hex. HEAD therefore still performs 59,220 such formats in Miri; the timed-out version performed 225,036. This is unnecessary interpreted allocator and formatting work unrelated to validating arithmetic or unsafe memory operations.

Use assertion formatting arguments directly, or build the detailed context only in an explicit mismatch branch. Rust's assertion macros format failure arguments only on failure. Validate by running the exact select test under Miri and comparing elapsed time; do not assume a particular speedup from source inspection. This is a stronger first change than removing more edge cases.

## P1: parity fails in reproducible, like-for-like cells

Primary evidence: [full performance run 45242934789](https://github.com/anne-skydancer/neoj2k-rust/actions/runs/45242934789), three repetitions, Rust `d5c164e`, pinned C++ v0.1.3 `00f273d502d211905adb756d2f75ef74321983d0`. `git diff d5c164e HEAD --stat` contains only the performance workflow, benchmark documentation, summary script and MQ test changes: **no production codec code differs**. Raw artifacts were reprocessed using HEAD's corrected `tools/perf_summary.py`, excluding worker counts greater than the runners' four logical CPUs. Complete regenerated tables are in [audit evidence](audit-2026-11-23/performance.md).

| Comparable cell | Faster | Within noise | Slower | Eligible rows |
|---|---:|---:|---:|---:|
| Linux GCC 15, baseline Rust / scalar C++ | 8 | 1 | 12 | 21 |
| Linux GCC 15, x86-64-v3 Rust / AVX2 C++ | 4 | 1 | 16 | 21 |
| Windows MSVC, x86-64-v3 Rust / AVX2 C++ | 10 | 5 | 6 | 21 |

Specific Linux v3 failures include 1,024² RGB decode at one worker **+2.0%** (spread +0.7 to +2.2), two workers **+5.2%** (+4.9 to +6.1), 64² RGB reduce-2 decode **+13.3%** (+13.0 to +13.5), 128² RGBA reduce-2 **+13.9%** (+13.7 to +14.1), and all six small encodes **+3.0% to +8.0%**. Conversely, the 4,096² gray large decodes are faster on Linux v3, and the Windows v3 encoder rows are faster. There is no defensible single claim that the entire Rust codec is slower on every platform.

Important boundaries:

- Windows baseline compares baseline Rust with AVX2 C++; exclude its overall parity counts.
- Eight-worker rows on four-CPU runners are oversubscribed. They are useful scheduling stress evidence, not proof of scaling on eight available CPUs.
- Run `45257669147` is a quick smoke run. Its one-repetition figures are not a replacement for this evidence.
- `doc/bench.md:97` onward describes an older pre-port baseline. Its 30–73% small-encode deficits must not be presented as current HEAD measurements.
- Rust and C++ standalone Tier-1 benchmarks time different work. Their absolute cycles cannot isolate the MQ kernel or prove how much of a gap comes from a particular loop.

Recommended remedy: prioritize Linux reduce-2 small-decode fixed costs and Linux encoder profiling, then same-process matched benchmarks for targeted changes. Retain output identity checks and controls. A source-level optimization is a hypothesis until measured with a quiet runner and a matching CPU/SIMD level.

## P2: warm parallel decode still allocates

Locations: `neo-j2k/src/decode.rs:632`, `neo-j2k/src/decode/blocks.rs:223`, `neo-j2k/src/dwt.rs:386`, `:528`, `:675`. C++ comparison: adjacent `neo-j2k/src/dwt.cpp:1827`–`:1948`.

The staged component path constructs a fresh vector of reconstruction planes per tile. Parallel Tier-1 constructs a fresh row-cost vector. Parallel wavelets construct vectors of mutable row slices per level; population runs serially over rows and stripes before worker execution. For 9/7 lifting the table size is proportional to `height * stripe_count`, and interleaving builds another row map. C++ computes stripes from pointer offsets and uses retained scratch rather than constructing Rust mutable-slice tables for every level.

A local release reproduction used `large_1024_rgb_97.j2k`, typed caller I32 planes, 256 MiB retained capacity and three warm-up decodes. A global allocator counted only the next decode. Its valid inline executor reports the requested concurrency and executes all job indices synchronously, deliberately excluding thread-pool allocation and timing effects:

| Reported concurrency | Baseline allocations / reallocations | x86-64-v3 allocations / reallocations |
|---|---|---|
| 1 | 0 / 0 | 0 / 0 |
| 2 | 14 / 0 | 14 / 0 |
| 4 | 14 / 0 | 14 / 0 |
| 8 | 14 / 0 | 14 / 0 |

The source-only reproduction is [allocation-repro.rs](audit-2026-11-23/allocation-repro.rs). These counts demonstrate codec allocations after warm-up; they **do not measure parallel speed**, and they do not establish that allocations explain the entire observed latency gap. The temporary repro package used ordinary Cargo release defaults, not the workspace's fat-LTO release profile; allocation existence was unchanged at either CPU level.

Recommended remedy: reuse owning metadata such as row costs in workspaces; use fixed-capacity storage for bounded component counts where practical; investigate safe task partitioning that reduces slice-table construction. Borrowed mutable references cannot simply be retained across calls, so avoid forcing a cache with invalid lifetimes or introducing unreviewed unsafe pointer arithmetic. Measure table construction separately before a redesign.

`small_image_gates.rs:166` tests zero heap calls only for small serial decodes. Its thread-local measurement is intentionally local to that thread. It does not assert zero allocations for parallel decodes. Add a focused parallel allocation measurement if zero warm allocation is an intended requirement; the current small-decode test is not broken merely because it has narrower scope.

## P3: small I32 comparison includes a Rust output copy

Locations: `neo-j2k/tests/small_image_gates.rs:113`–`:151`, `:277`–`:317`; `neo-j2k/src/decoder.rs:612`–`:624`; `neo-j2k/src/decode.rs:274` and `:1064`.

Small decode timing selects `PlanarI32::decode`, which calls the byte-oriented `Decoder::decode_into(..., SampleType::I32, ...)`. That path reconstructs owned planes and writes them into byte buffers afterward. C++ writes into its I32 output directly. The large benchmark already uses Rust `decode_into_i32`, allowing direct reconstruction for a matching single tile.

The small table validly measures those exposed API paths, but the phrase “caller-owned native-endian planar I32 on both sides” can be read as matching reconstruction strategies when it does not. This is a documented API implementation cost, not evidence of incorrect decoding or a claim that unsafe casting should be added to the byte API.

Add a typed-I32 small suite with the same lifecycle and output checks. Keep the existing byte suite for callers who need byte layouts. Compare typed and byte results within the same process before attributing reduce-2 deficits to Tier-1. The byte copy may explain some overhead, but no causal percentage was established in this audit.

## P4: reusable encoder parity remains unmeasured

Location: `neo-j2k/tests/small_image_gates.rs:448`–`:518`; `neo-j2k/src/encoder.rs:123`–`:150`.

The small encoder comparison constructs and destroys `Encoder::new()` for every timed invocation, matching the C++ shim's construction lifecycle. This is a reasonable cold-request comparison, and output bytes are checked before timing. It does not measure the reusable encoder advertised by the public API. C++ also copies input/output across the shim boundary; precise kernel attribution requires matching that work too.

Add a reused-encoder comparison on both sides and large encode rows with a C++ side. Do not infer whole-encoder parity from the current Rust-only executor scaling test, nor assume Linux encoder deficits can be fixed by a decoder optimization. The compiler-dependent encoder result (Linux slower, Windows faster) merits profiling and generated-code comparison before redesigning the encoder.

## D1: redundant coefficient-plane clearing deserves a measured check

Location: `neo-j2k/src/decode.rs:1064`–`:1074`, with the block walk in `neo-j2k/src/decode/blocks.rs:132` and empty-block stores in `neo-j2k/src/t1.rs:174`.

Owned reconstruction resizes then fills the entire coefficient plane with zero before the block walk. Direct reconstruction intentionally skips this clear, with a comment that every block writes its samples and missing blocks write zero. This makes the owned clear a candidate for removal. It also adds memory traffic specifically to the byte-output path discussed above.

Before removal, demonstrate complete coverage for odd origins, subsampling, partial/truncated packets, reduced resolutions and empty bands, using nonzero poison in retained buffers. Reuse existing parity cases to validate output. This audit did not remove the clear or independently prove coverage for every accepted malformed geometry; no specific throughput gain is claimed.

## Rust design and correctness observations

The maintained core uses safe borrowing for worker writes and confines intrinsic unsafety to `src/simd/`. Inspected SIMD loads/stores use sized arrays or checked slice ranges. Intrinsics are selected at compile time, not by a runtime feature detector; build flags must match deployment CPUs. The mutex-slot executor safely transfers disjoint mutable jobs and completes omitted indices, at the cost of bounded per-batch synchronization. These are explicit design tradeoffs, not sufficient evidence of “bad Rust.”

The C++ arena accounting model (`src/mem/`) duplicates conceptual allocations while Rust stores data in vectors. This adds complexity but serves documented status and memory-accounting parity tests. Removing it solely as “overengineering” would alter an intentional compatibility requirement. Its modeled byte count is not an RSS bound.

The stream buffer is explicitly outside the working-memory budget (`src/decoder.rs:534`, `src/stream.rs:174`). A caller decoding untrusted large streams must separately bound advertised input length. A separate input-buffer limit would be useful if comprehensive memory bounding is a product objective; this is a documented limitation, not a newly discovered violation of `Limits::max_memory`.

Hot Tier-1 row/lane loops and runtime context indexing merit generated-code profiling (`src/t1/passes.rs:126`, `src/t1/mq.rs:166`). Bounds checks, register spills and missed specialization are plausible optimization leads, but this audit did not establish their emitted instruction costs. The earlier IDE scratchpad audit's assembly claims were not treated as new verified findings.

## Validation and limitations

Executed locally with rustc/cargo 1.100.0 on Windows:

1. Native execution of Miri-selected code: `NJ2K_ORACLE_NO_BUILD=1`, `RUSTFLAGS=--cfg miri`, separate target directory; `cargo test --locked -p neo-j2k -p neo-j2k-testkit --lib`: **60 codec + 24 testkit tests passed**. `cargo test --locked -p neo-j2k --test miri_decode`: **2 passed**. This checks selected test logic with debug overflow checks. It is **not a Miri run** and establishes no interpreter UB or data-race coverage.
2. Warm allocation reproduction in release, baseline and `-C target-cpu=x86-64-v3`: counts above.
3. `python -I tools/perf_summary.py selftest` and `python -I tools/bench_tier1.py --selftest`: both passed. The summary self-test deliberately prints an incomplete-result fixture before reporting success.
4. CI raw performance artifacts reprocessed with the current summary script; full tables saved alongside this report. Previous Miri log and check annotation reviewed.

A plain native `cargo test --lib` with `NJ2K_ORACLE_NO_BUILD=1` fails to link oracle differential tests; those tests are intentionally excluded by `cfg(miri)` in the workflow. This was not classified as a production defect. No full local C++ differential suite, new native throughput campaign, full fuzz campaign or 45-minute Miri rerun was performed. No dependencies were changed, no fixes were committed, and this audit is not a blanket correctness certification.

Suggested execution order: eliminate eager failure-message formatting; verify and isolate Miri safety checks; establish typed small-decode and reusable-encoder comparisons; profile Linux fixed costs; remove measured warm parallel allocations and serial metadata work; validate each change for exact output parity and repeat the relevant performance cell.
