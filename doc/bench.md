# Tier-1 benchmark

What it measures, how to run it, and what its table means. The benchmark times the two Tier-1 entry points of the
crate, decoding a code-block and encoding a code-block, in TSC cycles on one pinned CPU. It decides whether a change
to Tier-1 is faster; it says nothing of whole-image speed (the README's performance tables).

## What is in it

| Piece | Where | What |
|---|---|---|
| Entry points | `neo-j2k/src/bench.rs`, `neo-j2k/src/encoder/bench.rs`, behind the feature `bench-internals` | `DecodeWorkspace::decode` and `EncodeWorkspace::encode`: thin calls of what the decoder and the encoder run, with the buffers kept by the caller. Off by default, hidden from the documentation, not API. The crate's `unsafe` stays in `src/simd/`. |
| Measuring program | `neo-j2k-bench/` (an unpublished workspace crate, `publish = false`) | One run is one round of one build: it pins itself, times every set and prints one `RESULT` line each. Reads the TSC (`_rdtsc`) and sets the thread's affinity, so it is, besides the oracle and the fuzz crate, a crate that holds `unsafe`; it has no dependency but the codec and the test kit, and never the C++ oracle. |
| Driver | `tools/bench_tier1.py` | Builds the base, the head and a copy of the base, runs the three alternately, prints the table. |

`tools/check_rust_native.py` checks that the crate does not depend on the benchmark crate, that every workspace crate
but `neo-j2k` is `publish = false`, and that `bench-internals` is not a default feature. `cargo deny` covers the
benchmark with the rest of the workspace: it has no third-party dependency.

## The sets

| Set | Input | Time |
|---|---|---|
| `decode/256_lossy`, `decode/256_lossless`, `decode/512_*`, `decode/1024_*` | the six dumps of `tests/vectors/t1_bench` of the C++ repository (75, 75, 179, 210, 718 and 777 code-blocks of one synthetic texture, the viewer's upload parameters), read from `NJ2K_CPP_SOURCE`, never copied here | one pass over the file's blocks: `DecodeWorkspace::decode`, including the store into the tile buffer (the C++ bench times `t1_decode_cblk` alone) |
| `encode/lossy`, `encode/lossless` | 256 synthetic 64 x 64 blocks of a Laplacian-like high band, regenerated by the generator of `bench/nj2k_enc_t1_ratio.cpp` (a fixed seed; "lossy" the 9/7's small sparse samples with a dead zone, "lossless" the 5/3's larger ones) | one pass over the blocks: `EncodeWorkspace::encode` |

A dump does not say its wavelet: a file named `lossless` is stored as 5/3, the others as 9/7 with a step of 1.0.
Before timing, a run decodes or encodes every block once and prints a hash of the output (`digest`); the driver
compares the three builds' hashes.

## Running it

```
python -I tools/bench_tier1.py --base-ref origin/main                  # the head is this working tree
python -I tools/bench_tier1.py --base-ref v0.1.3 --head-ref my-branch   # or a ref
python -I tools/bench_tier1.py --base-exe base.exe --head-exe head.exe  # executables built beforehand
```

| Option | Default | |
|---|---|---|
| `--base-ref` | `origin/main` | The baseline. It must contain the benchmark crate (the driver copies the head's `neo-j2k-bench/src` into the base's tree, so that only the codec differs). |
| `--head-ref` | the working tree | Build another ref as the head. |
| `--rounds` | 24 | Rounds of the three builds, after one warm-up round; a multiple of six, so that each of the six orders the builds run in is taken equally often. |
| `--pin` | the last logical CPU | The logical CPU (Windows: of the first processor group). The program says in its first line whether it is pinned; a build that is not stops the run, unless `--allow-unpinned`, which runs on and writes UNPINNED in the environment line. |
| `--cpu` | `baseline` | `x86-64-v3` builds all three with `-C target-cpu=x86-64-v3`. |
| `--cpp-source` | `NJ2K_CPP_SOURCE` | The C++ neo-j2k checkout, for the six dumps. Any v0.1.3 checkout will do; the pinned commit is in the README. |
| `--min-mcycles`, `--units` | 30, 3 | A timed unit repeats the pass until it takes at least this many Mcycles; the median of this many units is a round's figure. |
| `--strict` | off | Exit 1 when the gate is No. |
| `--workdir`, `--keep` | a temporary folder, removed | The builds (git worktrees and target folders). |

`python -I tools/bench_tier1.py --selftest` checks the table's arithmetic and gate without building anything (CI runs it).
The program alone: `neo-j2k-bench --pin 7 --min-mcycles 30 --units 3 --dumps DIR` prints the `RESULT` lines of one
round; `--digest-only` prints the output hashes without timing (CI's smoke run).

## The table

One table, every figure a percent change against the base (minus is faster), and Yes/No columns:

| Column | Meaning |
|---|---|
| Base (Mcycles) | The base's cycles of one pass, the median of the rounds |
| Head vs base | The percent change of the head's cycles against the base's in the same round, the median over the rounds (rounded to two decimals; the gate reads the rounded figure) |
| Head, rounds min to max | The smallest and the largest of the rounds' changes: how far one round strays |
| Control vs base | The same for a byte-for-byte copy of the base's executable: the noise of the method |
| Control, rounds min to max | The same range for the control |
| Output identical | The three builds' output hashes are equal |
| Gate | Yes when the head is at least 3.0 % faster, the control is within +-1.0 %, and the outputs are identical |

The builds run alternately in one process-per-round loop, in all six orders in turn, so no build keeps a position or
a stretch of the machine's drift; the comparison is within a round. The control is the same executable, run in the
same loop: a control outside +-1.0 % says the machine was too noisy to read the head's figure, whatever it is.

The control is a byte copy of the base, so it sees the run-to-run noise of the machine and nothing else. The head is a
different binary: moving code changes its layout and alignment, which can move a figure by a few percent without any
change in what the code does. This is why the gate is 3.0 % and a result near it is measured again (another pin, another
day) before it is believed; no separate build of the base from another path is needed as a second control.

## Caveats

- TSC cycles are ticks of a constant-rate counter, not core cycles: a change of clock speed during a run moves both
  builds in a round alike, but a run on a machine that parks cores or changes frequency in steps is noisy. Pin to a CPU
  that is not busy, close other programs, and read the control first.
- The pass is long (30 Mcycles or more a unit) but not isolated from the operating system: 24 rounds and the median
  take most of that out, not all. A short smoke run (`--rounds 3 --min-mcycles 2`) proves the program works and
  proves nothing about speed.
- The decoder sets time the store as well as `t1_decode_cblk`, and the encoder sets the copy of the samples in and of the
  passes and bytes out as well as `enc_t1_encode`; a change that only touches those moves them.
- The encoder sets are 64 x 64 blocks of two textures; a change that helps another kind of block (a sparse one, a
  small one) may not show.
- Absolute cycles depend on the CPU and on the build (`baseline` against `x86-64-v3`): compare builds of one run, not
  runs on two machines.
- Linux needs nothing beyond glibc for the pinning. Other systems run unpinned (the program says so) and the
  clock is nanoseconds.

## Baseline against neo-j2k C++ 0.1.3 (2026-11-23)

The whole codec and the Tier-1 kernel of this repository at 0.1.3 (`main` at 336b766) against neo-j2k C++ v0.1.3 (commit 00f273d), before the Tier-1 steps of the C++ 0.1.3 that this port does not have yet (the decoder's select decision, its run absorption and the sign/significance split; the encoder's cleanup mask and refinement pair list). The Rust tables of the README ("Native Rust versus neo-j2k C++") were measured against earlier C++ code, before that redesign, and do not describe 0.1.3.

Machine and method: Ryzen 9 9950X3D, Windows 11, rustc 1.100.0, MSVC 19.51 (the C++ oracle, `RelWithDebInfo`, built `NJ2K_SIMD=SCALAR` for the baseline CPU level and `AVX2` for `x86-64-v3`), release builds with fat LTO and one code-generation unit, pinned to logical CPU 7, three repetitions of each suite (the medians below; the spread is the lowest and highest of the three). Before each of the 80 timed runs the other-process load over 2 s was at most 10 % (9 waits of 30 s in all; highest reading 9.1 %). Change is Rust's time against C++'s, minus is faster than C++.

What the baseline says: against C++ 0.1.3 the Rust twin is about level or faster on large baseline-CPU decodes (the C++ scalar wavelet is slow), slower on `x86-64-v3` 1,024² decodes (+4.5 % to +19.4 %) and on the small RGBA decodes, and 30 % to 73 % slower on every small encode in both builds. The Tier-1 kernel is the cause of most of the encode gap (Tier-1 is 86 % to 95 % of an encode). The port of the C++ steps is staged to close it, each stage gated at 3.0 % faster than before; the README's Rust-against-C++ tables are re-measured after it.

## Verifying a Tier-1 change in CI

`.github/workflows/tier1-verify.yml` runs on a pull request that touches the Tier-1 files (`neo-j2k/src/t1*`,
`neo-j2k/src/encoder/tier1*`), the oracle crate, the runner, the mutation lists, `Cargo.toml` or the workflow itself. It
is not part of `ci.yml`: its jobs are long.

| Job | What it proves |
|---|---|
| Mutation lists | Every pattern of `tools/mutations/*.json` occurs the stated number of times in the checked-out code (no build). |
| Tier-1 sweeps against the C++ (baseline, x86-64-v3) | The long comparisons with the C++ oracle (`nightly_`, six tests: every decision of the MQ decoder and encoder, the flush, the long code-block draws) pass at both CPU levels. |
| Tier-1 mutations (shard 1 to 4) | Each mutation of the lists, applied to a scratch copy, makes the tests it names fail. The tests run in the `mutation` profile of `Cargo.toml` (no LTO, `opt-level = 1`, debug assertions and overflow checks off, as in the release builds the tests normally run in), in the baseline CPU level. The list is split in four by the mutation's number modulo four. A survivor is printed as possibly an equivalent mutant and fails the job. |
| Tier-1 benchmark | By hand only, see below. A confirmation on a shared runner, not a gate. |

Each shard writes a table to the job's summary: the mutation, killed Yes or No, the test that killed it, and the seconds.

To run it by hand on a branch (once the workflow file is on `main`), and with the benchmark against `origin/main`
(12 rounds, the control included, pinned to the runner's last CPU):

```
gh workflow run tier1-verify.yml --ref my-branch
gh workflow run tier1-verify.yml --ref my-branch -f bench=true
```

To add a mutation list, write `tools/mutations/NAME.json` in the format of `tools/mutations/README.md`, run
`python tools/tier1_mutations.py --list` (it builds nothing) and commit the list in the pull request of the code it
tests, never ahead of it. The same script runs the mutations locally (`--only TEXT` for one), and builds a lot: it
is meant for CI.
